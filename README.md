### 실험 조건
- 데이터 크기 n = 1,000 / 2,000 / 4,000 / 8,000 / 16,000 / 20,000
- 데이터: `srand(2026)` 후 `rand() % 100000`으로 생성(중복 허용). 크기마다 seed를 다시 지정하고, 모든 알고리즘은 같은 원본의 복사본을 정렬한다.
- 랜덤 피벗은 `srand(12026)`으로 매번 초기화해서, 반복 실행과 알고리즘 순서에 상관없이 같은 피벗 순서를 사용한다.
- 각 (n, 알고리즘)을 400번 반복하고 평균 시간을 출력한다.
- 검증: 매 반복마다 `qsort` 결과와 `memcmp`로 비교한다. 6개 크기 모두 `PASS`였다.
- 참고: 실행 환경에 따라 `RAND_MAX`가 다르다(Windows는 32767인 경우가 많다). 이 경우 값의 범위가 좁아져 중복이 많아진다. 아래 결과는 제출 환경에서 실제로 측정한 값이다.

## 3. 측정 방법과 계산 기준

### 비교 횟수
데이터 값끼리 비교할 때마다 `s->comparisons++`를 실행한다. 반복문의 인덱스 검사와 종료 조건(`i <= mid`, `j < right` 등)은 세지 않는다.
- 힙 정렬: 힙 구성과 정렬 단계 모두에서 `sift_down` 안의 두 비교(두 자식 중 큰 값 고르기, 부모와 큰 자식 비교)를 센다.
- 병합 정렬: `merge`에서 `a[i] <= a[j]`를 비교할 때만 센다. 한쪽이 먼저 끝난 뒤 남은 원소를 복사하는 과정에는 비교가 없다.
- 퀵 정렬: 분할 과정의 `a[j] <= pivot` 비교와, Median-of-Three 피벗 선택의 비교(2~3회)를 센다.

### 실행시간
- `clock()`(CPU 시간)으로 `run_sort()` 호출 직전과 직후만 측정한다. 데이터 생성, `memcpy` 복사, 검증, 출력은 제외한다.
- 짧은 실행시간에서 타이머 해상도의 영향을 줄이기 위해 400회 측정값의 평균을 사용하였다. 평균값의 소수 자릿수가 개별 측정의 정확도를 의미하는 것은 아니다.
- 같은 프로그램을 다시 실행했을 때 비교 횟수와 메모리는 완전히 같았지만 시간은 달랐다(예: n=8,000의 Quick(First)가 1.06 ms와 1.205 ms). 따라서 작은 시간 차이만으로 성능의 우열을 일반화하기 어렵다. 측정 오차 범위를 정량적으로 계산하지는 않았다. 2장의 표와 분석은 마지막 실행 결과 기준이다.

### 메모리 사용량 (직접 계산, sizeof 합산 모델)
- 함수가 호출될 때 그 함수의 매개변수와 지역변수 크기를 `enter_memory()`로 더하고, 끝날 때 `leave_memory()`로 뺀다. 도중에 가장 컸던 값이 `peak_memory`이다.
- 사용한 크기: `sizeof(int)=4`, 포인터 `8`, `sizeof(Algorithm)=4`.
- 원본 배열, 반환 주소, 컴파일러 패딩, 통계 구조체 자체는 계산에서 제외한다. 따라서 실제 스택 사용량이 아니라 같은 기준으로 알고리즘을 비교하기 위한 추정값이다.
- 계산 예:
  - 힙 정렬: `run_sort`(24) + `heap_sort`(28) + `sift_down`(32) + `swap`(28) = **112 B**. 재귀가 없어서 n과 무관하다.
  - 병합 정렬: `run_sort`(24) + `merge_sort`(28) + 임시 배열(4n) + 재귀 프레임(36 B × `merge` 호출 시점에 동시에 존재하는 `merge_recursive` 호출 수) + `merge`(48) = 4n + 100 + 36 × ⌈log2 n⌉. n=20,000이면 80,000 + 100 + 36 × 15 = **80,640 B**로 출력값과 일치한다. 이 식은 이 프로그램의 변수 구성과 재귀 방식에 대한 계산식이며, 병합 정렬 일반에 대한 공식은 아니다.
  - 퀵 정렬: 이 구현에서 분할 중 최대 메모리는 24 + 32D + (`partition` 44 + `choose_pivot` 32) = 100 + 32D로 계산된다. D는 해당 시점에 동시에 존재하는 `quick_recursive` 호출 수이다(종료 조건에서 바로 끝나는 호출의 깊이와는 구분한다).

## 4. 비교·분석

### 4.1 데이터 크기 증가에 따른 비교 횟수 변화
n이 1,000에서 20,000으로 20배 늘 때 `n log2 n`은 약 28.7배 늘어난다. 실제 비교 횟수는 힙 30.4배, 병합 30.0배, 퀵(First) 30.1배, 퀵(Random) 32.3배, 퀵(Median3) 29.5배로, 세 알고리즘 모두 O(n log n)에 가깝게 증가했다(n²이었다면 400배).

`비교 횟수 / (n log2 n)` 값은 알고리즘마다 거의 일정한 상수에 가깝다.

| 알고리즘 | n=1,000 | n=20,000 |
|---|---:|---:|
| 병합 정렬 | 0.87 | 0.91 |
| 퀵(First / Random / Median3) | 1.13 / 1.04 / 1.09 | 1.19 / 1.17 / 1.13 |
| 힙 정렬 | 1.69 | 1.79 |

- **병합 정렬**이 비교 횟수가 가장 적다. 배열을 반으로 나눠 이미 정렬된 두 부분을 합칠 때, 한쪽이 끝나면 나머지는 비교 없이 복사하므로 n log2 n보다 조금 적게 비교한다.
- **힙 정렬**은 병합 정렬의 약 1.93~1.96배로 가장 많다. `sift_down`은 한 단계에서 두 자식 중 큰 값을 선택하고 부모와 비교하므로, 최대 두 번의 값 비교를 수행한다. 또한 최댓값을 제거할 때마다 힙 속성을 복구하기 위해 여러 층을 내려갈 수 있어 비교가 반복된다.
- **퀵 정렬**은 그 중간이다. 분할마다 피벗을 제외한 구간의 각 원소를 피벗과 한 번씩 비교하며, 피벗의 위치에 따라 두 부분의 크기가 달라진다. 퀵 정렬의 비교 횟수는 이번 실험에서 병합 정렬보다 약 19~40% 많았다.

### 4.2 실행시간 차이
n=20,000에서 시간은 힙 3.91 ms, 병합 2.69 ms, 퀵 2.60~2.89 ms이다. 모든 크기에서 힙 정렬이 가장 느렸고 병합 대비 1.38~1.63배였다. 비교 횟수 비율(약 1.95배)보다 시간 격차가 작은 이유는 비교 한 번의 비용이 같지 않기 때문이다. 병합 정렬은 임시 배열로 복사하는 비용(`temp`에 쓰고 `a`로 되돌림)이 따로 있어서, 비교는 적어도 이동 비용이 시간에 더해진다.

힙 정렬이 불리한 또 다른 이유는 메모리 접근 방식이다. `sift_down`은 `2*root+1`로 인덱스를 건너뛰며 배열의 멀리 떨어진 위치를 접근한다. 반면 병합 정렬과 퀵 정렬은 배열을 앞에서 뒤로 순서대로 훑기 때문에 캐시를 잘 활용한다. 이 부분은 이번 실험에서 캐시 미스를 직접 측정하지는 않았으므로 일반적으로 알려진 원인을 근거로 한 설명이다.

병합 정렬과 퀵 정렬은 시간 차이가 작았다(n=20,000에서 2.60~2.89 ms). 퀵 정렬은 비교 횟수가 병합보다 많지만 임시 배열 복사가 없고 교환만 하기 때문에 시간이 비슷해졌다. n=8,000에서는 병합이 가장 빠르고(1.01 ms) 퀵(Median3)이 n=16,000, 20,000에서 가장 빨라서 순위가 일정하지 않다. 시간 차이가 작고 순위가 일정하지 않으므로 어느 쪽이 항상 빠르다고 일반화하기는 어렵다.

### 4.3 메모리 사용량 차이

| n | 힙 | 병합 | 퀵(First) | 퀵(Random) | 퀵(Median3) |
|---:|---:|---:|---:|---:|---:|
| 1,000 | 112 | 4,460 | 740 | 772 | 644 |
| 20,000 | 112 | 80,640 | 1,252 | 1,092 | 900 |

- **힙 정렬**은 입력 배열 안에서 교환만 하고 반복문으로 구현했기 때문에 n이 20배 늘어도 112 B로 그대로이다(공간 O(1)).
- **병합 정렬**은 크기 n짜리 임시 배열이 필요해서 n에 정비례한다(약 4n B). n=1,000에서 4,460 B, n=20,000에서 80,640 B로 약 18배 증가했다. 재귀 스택은 36 × ⌈log2 n⌉ B로 임시 배열에 비해 작다.
- **퀵 정렬**은 추가 배열은 없으며, 재귀 호출 스택과 분할·피벗 선택에 필요한 보조 변수를 사용한다. 메모리가 n에 정비례하지 않고 동시 재귀 호출 수에 따라 달라지며, 이번 실험에서는 최대 1,252 B였다. 이는 같은 크기에서도 피벗에 따라 깊이가 달라진다는 뜻이다(4.4 참고).

### 4.4 퀵 정렬의 피벗 선택 방법에 따른 차이
- **비교 횟수**: n=4,000 이상에서는 Median3의 비교 횟수가 가장 적었다(n=20,000에서 321,604회). 비교 횟수가 가장 많은 방법은 n=8,000에서 Random이었고, 나머지 세 크기(4,000 / 16,000 / 20,000)에서는 First였다(n=20,000에서 339,846회, Median3와 약 5.7% 차이). 그러나 n=1,000에서는 Random이, n=2,000에서는 First가 가장 적었고 Median3가 오히려 가장 많았다. 입력이 무작위일 때는 어느 피벗이든 평균적으로 비슷하기 때문에, 크기별 순위가 바뀌는 것은 특정 입력에서의 우연한 분할 차이로 보인다.
- **시간**: n=2,000 이상에서 Median3가 세 피벗 중 가장 빨랐다(n=16,000에서 2.02 ms 대 First 2.30 / Random 2.36 ms, n=20,000에서 2.60 ms 대 2.77 / 2.89 ms). 이는 비교 횟수가 적고 재귀 깊이가 얕은 것과 방향이 같다. Random은 `rand()` 호출 비용이 추가되어 n=8,000을 제외하고 대체로 가장 느렸다. n=1,000에서는 Random이 가장 빨랐는데, 이 크기에서는 시간 차이가 작아 일반화하기 어렵다.
- **메모리(동시 재귀 호출 수)**: 이 구현에서 분할 중 최대 메모리는 100 + 32D로 계산된다. D는 해당 시점에 동시에 존재하는 `quick_recursive` 호출 수이다. n=20,000에서는 First 36, Random 31, Median3 25였다(log2 20000 ≈ 14.3). Median3는 세 표본의 중앙값을 선택하여 극단적인 피벗을 줄이려는 방법이다. 이번 입력에서는 최대 동시 재귀 호출 수가 가장 적었지만, 항상 균형 잡힌 분할을 보장하지는 않는다.
- **한계**: 이번 실험의 입력은 무작위 데이터뿐이라 First 피벗의 약점(이미 정렬된 입력에서 O(n²))은 드러나지 않았다. 입력이 정렬되어 있었다면 First는 훨씬 나빠졌을 것이다. 이는 실험으로 확인한 결과가 아니라 알고리즘의 동작에서 예상되는 내용이다. 또한 이 과제는 중복 값을 허용하는데, 현재 Lomuto 구현에서는 모든 값이 같으면 세 피벗 방법 모두 분할이 한쪽으로 치우쳐 O(n²) 시간과 O(n) 재귀 공간이 필요할 수 있다.

### 4.5 시간 복잡도 및 공간 복잡도

| 알고리즘 | 평균 시간 | 최악 시간 | 공간 | 비고 |
|---|---|---|---|---|
| 힙 정렬 | O(n log n) | O(n log n) | O(1) | 제자리 정렬, 최악 시간 O(n log n) 보장 |
| 병합 정렬 | O(n log n) | O(n log n) | O(n) | 임시 배열 필요 |
| 퀵 정렬 | O(n log n) | O(n²) | 평균 O(log n), 최악 O(n) | 피벗이 나쁘면 분할이 한쪽으로 치우침 |

실험 결과와의 연결:
- 세 알고리즘 모두 비교 횟수가 n log n에 비례해 증가했다.
- 공간은 힙(상수) < 퀵(재귀 깊이) < 병합(n에 비례) 순으로 실험에서도 확인되었다.
- 시간은 병합 ≈ 퀵 < 힙 순이었다. 이론상 같은 O(n log n)이지만 상수 계수(비교 횟수, 복사 비용, 메모리 접근 패턴)가 달라 실제 시간 차이가 생겼다.

## 5. 결론
1. 비교 횟수는 병합 < 퀵 < 힙 순이고, 모두 O(n log n) 증가를 보였다.
2. 시간은 병합과 퀵이 비슷하게 빠르고, 힙 정렬이 병합 대비 약 1.4~1.6배 느렸다.
3. 메모리는 힙 정렬(112 B)이 가장 적고, 병합 정렬은 n에 비례해 가장 많이 쓴다. 퀵 정렬은 그 중간으로, 피벗 선택에 따라 재귀 깊이가 달라진다.
4. 무작위 데이터에서는 Median-of-Three가 비교 횟수, 시간, 동시 재귀 호출 수에서 대체로 유리했지만 차이는 크지 않았다.
5. 메모리가 충분하고 최악의 경우에도 O(n log n) 시간이 필요하면 병합 정렬, 추가 메모리를 최소화해야 하면 힙 정렬, 평균적으로 빠르고 메모리도 적게 쓰고 싶으면 퀵 정렬(Median3)이 적합하다.
